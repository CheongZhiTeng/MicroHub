| ------------------------ | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 01 Identity              | Supabase email delivery, confirmation, restricted registration, secure session persistence | Matching an email is not ownership; backend checks confirmation on every protected request. Recovery uses email OTP to support same-iPad Expo Go.       |
| 02 Membership            | Verified active profile, privileged role functions                                         | Role and committee position are separate. Application approval and invitation redemption must be atomic. Never accept a client role.                    |
| 03 Homework              | Active membership, private Storage, assignment authorization                               | Private feedback and files must be inaccessible to other students; group membership/version ownership require dedicated tests before V1.                |
| 04 Attendance            | Active membership, trusted RPC/Edge handler, transaction locks                             | Six digits have limited entropy: rate limit by account and server; hash and restrict codes; prevent concurrent duplicates.                              |

## Conflicts and assumptions

- The document places audit logs and suspension in V1 in one section; the user's MVP security requirements take precedence. Implement the security foundation during MVP.
- The detailed document requires submission history, basic statistics, invitations, attachments and committee positions in MVP. They remain MVP even where the shorter prompt says “complete homework” in V1.
- Account deletion requests are tracked in V2 per both roadmaps; no destructive deletion UI ships before retention rules are agreed. Privacy support before V2 is a documented school contact.
- Five navigation destinations are established in MVP. Events, resource library, full notifications and communication are V1/V2, explicitly unavailable until implemented, never shown with fake data.
- The source calls for 76 requirements; counting the numbered feature lists confirms exactly 76 (including the inapplicable multi-club row).
- Admin “partial” club editing and “authorized scope” are ambiguous. Initially only Super Admin edits club settings or technical roles; Admin reviews membership and later manages academic operations. Additional delegation needs an explicit permission specification.
- A valid school address is necessary but insufficient: verified ownership, non-suspended account and approved membership are independent gates.
- No Supabase project or school SMTP configuration is supplied. Build and test locally; do not invent deployment results.
